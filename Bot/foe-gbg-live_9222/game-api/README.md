# Бот оновлення великих споруд

## Найпростіша інструкція

Для однієї гільдії потрібен тільки **один комп'ютер із ботом**. Звичайним користувачам мобільного застосунку нічого встановлювати не потрібно.

Якщо ви налаштовуєте комп'ютер, на якому працюватиме бот, виконайте наведені нижче кроки по черзі.

### Крок 1. Встановіть Node.js

1. Відкрийте сайт [nodejs.org](https://nodejs.org/).
2. Натисніть кнопку завантаження версії **LTS**.
3. Відкрийте завантажений файл.
4. Натискайте `Next`, нічого не змінюючи.
5. Наприкінці натисніть `Finish`.

Це потрібно зробити лише один раз.

### Крок 2. Запустіть спеціальний Chrome

1. Відкрийте теку `game-api`.
2. Знайдіть файл `START-CHROME.cmd`.
3. Двічі натисніть на нього.
4. У новому вікні Chrome відкрийте Forge of Empires.
5. Увійдіть у потрібний ігровий акаунт.
6. Увійдіть у потрібний світ і дочекайтеся повного завантаження міста.
7. Не закривайте вкладку гри.

Цей проєкт використовує окремий профіль Chrome `ChromeFoEApi-9222`, тому авторизація не змішується з проєктом на порту 9223.

Важливо: у застосунку цей ігровий акаунт уже повинен бути зареєстрований як `GBGbot`. Якщо це ще не зроблено — попросіть адміністратора надати йому роль `GBGbot`.

### Крок 3. Налаштуйте бота

1. Поверніться в теку `game-api`.
2. Знайдіть файл `SETUP.cmd`.
3. Двічі натисніть на нього.
4. Зачекайте. Перше встановлення може тривати кілька хвилин.
5. Нічого не вводьте у чорному вікні.

Програма сама:

- знайде відкриту вкладку гри;
- визначить `playerId`;
- визначить світ;
- визначить `guildId`;
- перевірить у Firebase роль `GBGbot`;
- створить правильний `config.json`.

Усе гаразд, якщо в кінці написано:

```text
ГОТОВО. Налаштування перевірено. Тепер запустіть START-BOT.cmd.
```

Якщо роль не `GBGbot`, конфіг не буде створено. У вікні буде написано, що саме потрібно перевірити.

### Крок 4. Запустіть бота

1. Знайдіть файл `START-BOT.cmd`.
2. Двічі натисніть на нього.
3. Не закривайте чорне вікно.

Усе гаразд, якщо з'явився текст приблизно такого вигляду:

```text
Worker ... авторизований; Chrome=http://127.0.0.1:9222; режим=постійний
```

Після цього бот очікує команди від Firebase. Поки ніхто не відкриває екран ВС, він не надсилає запити до гри.

Окремо бот раз на хвилину перевіряє приватні повідомлення у Forge of Empires.

### Як надіслати повідомлення в чат застосунку через бота

1. Відкрийте приватну розмову з ігровим акаунтом `GBGbot` у Forge of Empires.
2. Щоб надіслати повідомлення від імені бота, використайте формат `Назва чату_Текст`.
3. Щоб надісати повідомлення від вашого імені, використайте формат `Назва чату_я_Текст`.

Наприклад, ця команда опублікує `Гонка` від імені бота:

```text
ПБГ_Гонка
```

А ця — від імені відправника:

```text
ПБГ_я_Гонка
```

Бот знайде у застосунку груповий чат `ПБГ` і додасть у нього повідомлення `Гонка` з обраним форматом автора.

Назва чату до `_` повинна точно збігатися з назвою групового чату в застосунку. Надіслати таку команду може лише учасник тієї самої гільдії. Звичайні приватні повідомлення без `_` бот ігнорує.

### Що має залишатися відкритим

Під час роботи бота:

- комп'ютер має бути увімкнений;
- комп'ютер не повинен переходити в режим сну;
- спеціальний Chrome має залишатися відкритим;
- вкладка Forge of Empires має залишатися відкритою;
- чорне вікно `START-BOT.cmd` має залишатися відкритим.

Після перезавантаження комп'ютера знову двічі натисніть спочатку `START-CHROME.cmd`, а потім `START-BOT.cmd`. `SETUP.cmd` повторно запускати не потрібно, якщо не змінився ігровий акаунт або гільдія.

### SOCKS5-проксі для Chrome 9222

1. Один раз запустіть `SETUP-PROXY-9222.cmd` і введіть пароль проксі у локальному вікні.
2. Пароль зберігається у `.proxy-9222.json` у зашифрованому Windows DPAPI вигляді та доступний лише поточному користувачу Windows.
3. Надалі запускайте Chrome звичайним файлом `START-CHROME.cmd`. Він автоматично підніме локальний міст `127.0.0.1:19222` до SOCKS5-проксі.
4. Перед запуском закрийте попереднє вікно Chrome 9222 повністю, інакше Chrome не застосує новий проксі.

Проєкт 9223 цим проксі не користується.

## Якщо щось не працює

### Написано, що Chrome недоступний

1. Закрийте всі вікна Chrome.
2. Знову запустіть `START-CHROME.cmd`.
3. Відкрийте гру та дочекайтеся появи міста.
4. Повторно запустіть `SETUP.cmd` або `START-BOT.cmd`.

### Написано, що не знайдено вкладку Forge of Empires

Гру відкрито не в тому Chrome. Відкрийте її саме у вікні, яке з'явилося після запуску `START-CHROME.cmd`.

### Написано про неправильну роль

Передайте адміністратору свій нік у грі та попросіть перевірити роль `GBGbot`. Звичайні ролі `bot`, `developer` або роль учасника для запуску worker не підходять.

### Вікно бота закрилося

Знову двічі натисніть `START-BOT.cmd`. Якщо воно закривається повторно, сфотографуйте текст помилки та надішліть адміністратору.

## Що відбувається автоматично

1. Користувач відкриває екран ВС у мобільному застосунку.
2. Застосунок створює Firebase-тригер.
3. Якщо останнє успішне оновлення було менше хвилини тому, нове сканування не запускається.
4. Бот отримує список усіх співгільдійців і короткі дані їхніх ВС.
5. Порівнюються тільки `level` та `currentProgress`. Зміна `maxProgress` окремо не враховується.
6. Вкладники запитуються лише для нових або змінених ВС.
7. Усі зміни записуються у Firebase одним пакетом.
8. Наприкінці бот показує час виконання.

Також раз на хвилину бот:

1. перевіряє свіжі приватні повідомлення FoE;
2. приймає лише повідомлення від співгільдійців;
3. розділяє команду за першим `_`;
4. знаходить груповий чат за точною назвою;
5. записує повідомлення у Firebase;
6. не публікує одне й те саме повідомлення повторно.

Раз на годину бот синхронізує склад гільдії з FoE:

1. порівнює склад FoE з локальним знімком;
2. якщо змін немає, не звертається до Firebase;
3. якщо зміни є, передає лише списки доданих, змінених і видалених гравців;
4. створює або виправляє `userName` та `imageUrl` у `guildUsers`;
5. для нового гравця створює запис у `users` із випадковим `password`;
6. додає новому співгільдійцю роль `member` у поточній гільдії;
7. виправляє `userName` та `imageUrl` уже наявного користувача;
8. не змінює наявні `password` і `role`;
9. не затирає `imageUrl`, якщо FoE не повернула аватар;
10. для гравця, який залишив гільдію, видаляє його запис із `guildUsers`;
11. видаляє поточну гільдію з `users/<userId>/userGuilds`, якщо користувач має інші гільдії;
12. видаляє весь `users/<userId>`, якщо інших гільдій немає;
13. записує всі зміни одного циклу одним атомарним пакетом.

Адреса аватара формується так:

```text
https://foe.scoredb.io/img/games/foe/avatars/<avatar>.jpg
```

Перед видаленням бот перевіряє, що повний список FoE містить його власний акаунт `GBGbot`. Якщо перевірка не пройдена, жодні зміни в Firebase не записуються.

Локальний знімок зберігається у `local-scan-cache/<worldName>_<guildId>-guild-members.json` і замінюється лише після успішного запису. Якщо він відсутній або пошкоджений, виконується повна звірка. Додатково повна контрольна звірка виконується раз на 24 години.

Якщо хоча б одна відповідь гри не отримана, часткові дані не записуються.

# Технічна інформація для адміністратора

## Автоматичне визначення конфігурації

Команда:

```powershell
npm run setup
```

перезавантажує відкриту вкладку FoE та читає:

```text
StartupService.getData.responseData.user_data.player_id
StartupService.getData.responseData.user_data.clan_id
```

`worldName` визначається з адреси вкладки, наприклад `ru11.forgeofempires.com`. Після цього викликається `authorizeBot` із `botType: "GBGbot"`. `config.json` записується лише після успішного підтвердження ролі.

## Ручні команди

```powershell
npm install
npm run setup
npm run worker
npm run worker:once
npm run check
npm test
```

`npm run worker` працює постійно. `npm run worker:once` виконує один повний цикл: перевіряє тригер ВС, склад гільдії, приватні повідомлення, ПБГ та кванти, а потім завершується.

Якщо ігрова вкладка недоступна довше кількох хвилин у кожному світі, worker
зупиняється з інструкцією замість того, щоб безкінечно робити марні запити
(поріг — `worker.sessionDeadExitMs`, типово 3 хвилини). `START-BOT.cmd` дублює
весь вивід у `local-scan-cache/worker.log`.

## Остаточна періодичність і сумісність із GuildChat

Worker записує дані у форматі, який читає застосунок GuildChat з гілки
`feat/widgets`. `{guildKey}` завжди формується автоматично як
`<worldName>_<guildId>`, наприклад `ru11_10821`; значення конкретної гільдії
не зашите в коді.

- карта і стан секторів ПБГ: раз на 10 секунд лише у стані `participating`;
- таблиця активності гравців ПБГ: раз на хвилину;
- очки та місця гільдій: о `HH:02` кожної години;
- повна контрольна перевірка споруд секторів: раз на 30 хвилин;
- сектор із вільними слотами: повторна перевірка через 5 хвилин і далі кожні
  5 хвилин, доки всі слоти не будуть зайняті;
- при досягненні `endsAt` польові цикли зупиняються, а бот повторює лише
  `GuildBattlegroundStateService.getState`, доки сервер не поверне наступний
  стан і `startsAt`;
- у міжсезонному стані до `startsAt` бот не надсилає жодних польових запитів;
- від `startsAt` стартові пакети повторюються кожні 10 секунд, доки одночасно
  не будуть отримані карта, суперники та сектори; після цього працюють звичайні
  сезонні цикли до нового `endsAt`;
- приватні повідомлення: раз на хвилину;
- склад гільдії: при запуску та раз на годину;
- повна контрольна звірка складу з Firebase: раз на 24 години;
- великі споруди: лише після зміни
  `guilds/{guildKey}/refreshTriggers/greatBuildings` застосунком;
- кванти: за запитом (див. нижче), а не постійно.

Перед кожним записом результат порівнюється з локальним JSON. Якщо відмінностей
немає, Firebase не викликається. Якщо відмінності є, вони надсилаються одним
пакетом, а локальний знімок замінюється тільки після успішного запису.

Шляхи ПБГ, сумісні із застосунком:

```text
guilds/{guildKey}/GBG/map
guilds/{guildKey}/GBG/stateId
guilds/{guildKey}/GBG/startsAt
guilds/{guildKey}/GBG/endsAt
guilds/{guildKey}/GBG/opponents/{clanId}
guilds/{guildKey}/GBG/sectors/{sectorCode}
guilds/{guildKey}/GBG/PlayerLeaderboard
```

Після отримання міжсезонного стану вузол `GBG` атомарно замінюється на
`{ stateId, startsAt }`. Це видаляє дані минулого сезону та
`gbgNotificationQueue`.

У `sectors/{sectorCode}` бот використовує поля застосунку: `owner`, `color`,
`openTime`, `army`, `gainAttritionChance`, `freeSlots`, `buildings` та
`availableBuildings`. Поле `owner` містить короткий `clanId`, а не
`participantId`. `participantId` зберігається окремо.

Стан квантів бот записує одним атомарним знімком за шляхом:

```text
guilds/{guildKey}/quantum
```

Гру по квантах бот чіпає лише коли це комусь потрібно (машина станів у
`runQuantumCycle`):

- **live** — хтось у застосунку відкрив екран квантової карти
  (`guilds/{guildKey}/guildUsers/{playerId}/presence` зі `state: "online"` і
  `screen: "QuantScreen"`). Повний цикл: карта + розширені дані відкритих вузлів +
  активність учасників, кожні 10 секунд.
- **light** — екран ніхто не тримає, але є підписки
  `guilds/{guildKey}/quantumStateNotifications/{nodeId}`. Тягнеться лише
  `GuildRaidsMapService.getOverview` (стани вузлів); каданс динамічний —
  будуються всі шляхи від відкритих вузлів до цільових вузлів підписок, береться
  найменший залишок прогресу і ділиться на стелю швидкості (1 бій = +10 прогресу,
  не швидше ніж 0.5 с/бій). Не частіше за 10 с, не рідше ніж до опівнічного вікна.
- **roll** — вікно `expiresAt` (00:00 MSK, точний час із `getState`) або
  останні 5 хвилин перед `endsAt`: 10-секундний каданс із оновленням `getState`,
  доки не прийде нова складність і нова карта.
- **discovery** — рейд не активний (`Pending`/`Finished`): `getState` раз на
  30 хвилин або сон до `startsAt`.
- **idle** — нічого з переліченого: жодного запиту до гри; перевірка сигналів
  присутності/підписок раз на кілька секунд по відповіді `great-buildings-refresh-claim`
  (поле `quantum: { viewers, notificationNodes }` від Cloud Function).

Присутність і підписки Cloud Function дзеркалить у compact-вузли
`guilds/{guildKey}/live/quantumViewers` та
`guilds/{guildKey}/live/quantumNotificationNodes` (тригери `trackQuantumPresence`
і `trackQuantumNotificationNodes`) і віддає їх воркеру разом із claim — без зайвих
запитів. Якщо Cloud Function ще без поля `quantum`, воркер лишається у постійному
`live`-режимі, як раніше.

Якщо дані не змінилися, Firebase отримує лише контрольне оновлення раз на хвилину.
Статична схема карти береться з `quantumMaps/{mapKey}/{difficultyLevel}` через поле
`templatePath`. Наявність шаблону визначається типом рейду, рівнем і вузлами;
`rotation` бот лише дописує, якщо його бракує, і ніколи не перезаписує (зокрема
виставлений вручну).

Локальний знімок квантів:

```text
local-scan-cache/{guildKey}-quantum-current.json
```

Перед обробкою активної квантової карти worker перевіряє її
`guildRaidsType` і `difficultyLevel` у локальному каталозі:

```text
local-scan-cache/quantum-maps-server-current.json
```

Якщо шаблон відсутній, worker формує його з відповіді
`GuildRaidsMapService.getOverview`, атомарно створює запис
`quantumMaps/{mapKey}/{difficultyLevel}` у Firebase та повторно завантажує
повний каталог `quantumMaps` у локальний знімок. Динамічний стан вузлів до
шаблону не записується.

Локальний знімок ПБГ:

```text
local-scan-cache/{guildKey}-gbg-current.json
```

## Початковий знімок нової гільдії

Для зовсім нової гільдії спочатку отримайте повний звіт:

```powershell
npm start -- guild-contributors
```

Потім виконайте:

```powershell
npm run firebase:bootstrap -- '.\results\guild-contributors-<guildId>-<дата>.json'
```

Для наступних оновлень bootstrap не використовується.

## Firebase-тригер

Мобільний застосунок при відкритті екрана ВС створює:

```text
guilds/<worldName>_<guildId>/refreshRequests/greatBuildings/<унікальний-requestId>
```

```json
{
  "requestedBy": "<playerId користувача>",
  "requestedAt": { ".sv": "timestamp" }
}
```

Cloud Function перевіряє членство користувача, об'єднує одночасні запити та застосовує cooldown 60 секунд. Стан задачі:

```text
guilds/<worldName>_<guildId>/refreshTriggers/greatBuildings
```

## Локальні знімки

Поточний стан:

```text
local-scan-cache/<worldName>_<guildId>-current.json
```

Попередній стан:

```text
local-scan-cache/<worldName>_<guildId>-previous.json
```

Current-знімок замінюється лише після успішного пакетного запису Firebase.
