# Авто-наведення: розміри canvas і нативні жести

## Чи гарантовано ширину 1024?

Ні. У поточному `FoeSyncProvider` немає контракту, який примусово задає грі
CSS-ширину 1024. `DESKTOP_UA` задає рядок user agent, а не розмір canvas.
Встановлений `react-native-webview` 13.15.0 за замовчуванням використовує
`scalesPageToFit=true`; його Android-реалізація вмикає `useWideViewPort` і
`loadWithOverviewMode`. Вони дозволяють широкий layout viewport і вписують
сторінку у WebView, але не встановлюють саме 1024.

Це випливає з реалізації `node_modules/react-native-webview/src/WebView.android.tsx`
і `android/src/main/java/com/reactnativecommunity/webview/RNCWebViewManagerImpl.kt`
у цьому пакеті та з офіційної документації:

- [WebSettings.setUserAgentString](https://developer.android.com/reference/android/webkit/WebSettings#setUserAgentString(java.lang.String)) — змінює user agent.
- [WebSettings.setUseWideViewPort](https://developer.android.com/reference/android/webkit/WebSettings#setUseWideViewPort(boolean)) — поведінка залежить також від viewport meta сторінки.
- [WebSettings.setLoadWithOverviewMode](https://developer.android.com/reference/android/webkit/WebSettings#setLoadWithOverviewMode(boolean)) — початкове вписування ширини сторінки.
- [Android: viewport вебсторінки](https://developer.android.com/develop/ui/views/layout/webapps/targeting#Viewport) — CSS viewport не тотожний фізичному екрану.

Повторювані 1024 на одному телефоні — спостереження, не гарантія WebView.
Зміна фізичного розміру WebView може змінити лише масштаб його відображення,
залишивши CSS-ширину гри тією самою. Canvas також має окрему роздільність
буфера (`canvas.width/height`); це не `getBoundingClientRect().width/height`.

## Формула й одиниці

Джерело формули — `src/services/foeAutoAim.js`. Еталон: скрол −673 **CSS px**
при ширині canvas 1024 **CSS px**, а не −673 фізичні пікселі телефона.
Розміри беруться зі свіжого `requestInteractionProbe()`, не з калібрування.

```js
dragX = (-673 / 1024) * canvasRect.width;
dragY = 2.5 * canvasRect.height;
tapX = canvasRect.left + 0.433 * canvasRect.width;
tapY = canvasRect.top + 0.231 * canvasRect.height;

nativeSwipeXRatio = dragX / visibleViewport.width;
nativeSwipeYRatio = dragY / visibleViewport.height;
nativeTapXRatio = (tapX - visibleViewport.offsetLeft) / visibleViewport.width;
nativeTapYRatio = (tapY - visibleViewport.offsetTop) / visibleViewport.height;
```

`visibleViewport` — `window.visualViewport`, із запасним шляхом через
`innerWidth/innerHeight` без offset, якщо API відсутнє. Нативний модуль множить
ці частки на фактичні `WebView.width/height`. Множити на DPR додатково не треба.
Знаменник нативного жесту — viewport, не canvas: вони можуть мати різні розміри.
Kotlin-коментар до `swipe`, який згадує canvas як знаменник, неточний;
фактична реалізація використовує весь WebView.

| Ширина canvas, CSS px | Скрол X, CSS px | Тап X від лівого краю canvas, CSS px |
| --- | --- | --- |
| 768 | −504.75 | 332.544 |
| 1024 | −673 | 443.392 |
| 1280 | −841.25 | 554.24 |

Y зберігає попередню перевірену користувачем поведінку: надлишковий скрол
до межі мапи та тап на частці 0.231 висоти. По X такої межі немає; базова
пропорція залишається емпіричною, але більше не залежить від фіксованих CSS px.

## Виконання й захист

- Android-автовхід з екрана поселення та кнопка «Авто-наведення» тепер
  використовують одну формулу. Збережена точка `calibPoints.ship` не є умовою
  Android-автовходу. Згода на синхронізацію й доступні `swipe`/`tap` необхідні.
- Тихий вхід перезавантажує гру для початкової позиції камери та чекає
  чинної евристики готовності (видимий стабільний canvas, кадри, прогрів).
  Це не прямий сигнал завершення завантаження від рушія гри.
  Дані корабля/ратуші використовуються лише в діагностиці,
  а не для обчислення екранного наведення чи вибору конкретного поселення.
- Якщо потрібна авторизація на порталі, чинний fallback показує форму
  входу й завершує тиху спробу, прибираючи екран завантаження над логіном.
- Перед скролом і перед тапами повторно перевіряються CSS-геометрія,
  покоління/документ WebView та зміни його нативного layout. Застарілі
  координати після resize не використовуються для наступного тапу.
  Це не синхронне скасування вже розпочатого нативного свайпу при повороті.
- Некоректні розміри, невидима ціль і жест за межами нативного ліміту
  відхиляються. Повторний вхід починається з перезавантаження, не з
  додаткового скролу по вже зсунутій камері.
- Клік сам по собі не є успіхом: зберігається чинний watcher відповіді
  сервера поселення (`entered`), таймаут і повідомлення про помилку.
- Ручний калібрований «Тест» та налагоджувальна прокрутка залишені окремо;
  на інших платформах попередній калібрований сценарій не змінений.

## Перевірка на одному телефоні

1. Перезавантажити JS у наявному dev-client з нативними `swipe` і `tap`.
   Kotlin, нативні залежності й реєстрація модуля цим патчем не змінюються;
   повторна нативна збірка для нього не потрібна.
2. Відкрити «Технічні дані поселення» → «Відкрити гру». На щойно
   завантаженій грі, не рухаючи камеру вручну, виконати «Авто-наведення».
   Перевірити `entered` та фактично отриману мапу поселення.
3. Перемкнути «Стиснути вікно». Це також перезавантажить гру; перемикач
   заблокований під час наведення. Повторити тест після завантаження.
4. У технічних даних порівняти повний і стиснутий заміри: нативний розмір
   у dp, canvas і viewport у CSS px, bitmap, DPR, обчислений скрол X.
   «Копіювати все» включає останні вісім замірів і журнал автовходу.
5. Перевірити тихий вхід/«Оновити» з екрана поселення в обох режимах.
   `debugShrink` застосовується також до тихого входу. Після тесту повернути
   повний розмір. Успіх — свіжа серверна мапа, не лише маркер чи `pan_done`.

Якщо в обох замірах ширина canvas = 1024, перевірено фізичне вписування
однакової CSS-сцени. Це **не** перевірка поведінки FoE при іншій логічній
ширині. Не потрібно скидати збережене калібрування для тесту: Android-автовхід
його не читає; воно залишається доступним для ручної діагностики.

## Межі підтвердження

`node --test src/services/foeAutoAim.test.js` перевіряє еталон 1024, ширини
768/1280, нативні ширини 720/1080/1440, DPR, зміщений canvas, visual viewport,
невалідну геометрію та resize. Це тести перетворення координат, не симуляція
камери FoE. У робочому середовищі немає підключеного Android-пристрою чи
емулятора; реального підтвердження нової формули грою тут немає.

Навіть частки не доводять влучання в об'єкт на будь-якій логічній ширині:
гра може показати більшу область сцени замість пропорційного масштабування.
[OpenFL підтримує різні режими масштабування Stage](https://books.openfl.org/openfl-developers-guide/display-programming/working-with-display-objects/setting-stage-properties.html);
активний режим камери FoE цим патчем не визначається. Перетворення координат
незалежне від фізичної роздільності; припущення про пропорційне розташування
корабля на іншій CSS-ширині потребує перевірки серверним `entered`. Якщо воно
не підтвердиться, наступний крок — виміряти масштаб/позицію сцени або
окремо перевірити фіксований логічний viewport; зміна лише коефіцієнта
не може дати універсальної гарантії.
